# JKLU CampusFlow Backend - Learning Notes

## Phase 0: Skeleton, Build, Toolchain, and Initial Schema
- **JDK & Compiler Compatibility**: While JDK 26.0.2 is the installed host runtime, Spring Boot 3.5.16 uses Spring Framework 6.2.x and repackaged ASM 9.7, which accepts up to bytecode version 65 (Java 21). Setting `<maven.compiler.release>21</maven.compiler.release>` enables seamless cross-compilation on JDK 26 without class format errors.
- **ByteBuddy & Mockito**: ByteBuddy requires `-Dnet.bytebuddy.experimental=true -XX:+EnableDynamicAgentLoading` to attach and mock classes cleanly when running on modern JVMs. Configuring this inside `maven-surefire-plugin` ensures tests run warning-free.
- **Flyway & btree_gist**: PostgreSQL 16 `btree_gist` extension is successfully enabled for both `campusflow` and `campusflow_test` databases. Flyway handles temporal range and integer range exclusion constraints (`tstzrange`, `int4range`) natively.
- **Test Database Hygiene**: Test profile runs against `campusflow_test` with `clean-disabled: false`, performing clean and migrate before integration tests. Dev profile has `clean-disabled: true` to prevent accidental production/dev data drops.

## Phase 1: Foundation - Auth, CSRF, Security, Error Handling, Demo Seed
- **Pure Server-Side Session Authentication**: Migrated completely away from Bearer tokens to native server-side `JSESSIONID` cookie sessions with session-fixation protection (`changeSessionId()`), 30-minute idle expiration, and full session invalidation on logout.
- **Decoupled Demo User Seeding**: Removed all static user credentials and plaintext demo passwords from Flyway SQL scripts. Demo users are created strictly at runtime via `DemoUserSeeder` in `demo`, `dev`, and `test` profiles using BCrypt-hashed passwords from `DEMO_USER_PASSWORD`.
- **Comprehensive Rate Limiting**: Implemented two tiers of rate limiting: 5 failed login attempts per 15-minute window returning HTTP 429 with `Retry-After`, plus global IP rate limiting (180 req/min).
- **Exact Contract Conformance**: Synchronized all authentication paths and JSON structures with `API_CONTRACT.md`. Mutating requests enforce standard CSRF verification via `CookieCsrfTokenRepository` (`XSRF-TOKEN` / `X-CSRF-TOKEN`).

## Phase 2: Campus Data, Timetable Upload, Availability Engine, Bounded Queries
- **Duplicate YAML root key is fatal**: SnakeYAML rejects duplicate top-level keys silently in some parsers but throws in Spring Boot; always merge new `spring.*` config into the existing `spring:` block — never append a second `spring:` block at the bottom of the file.
- **commons-csv 1.10+ requires commons-io at runtime**: `UnsynchronizedBufferedReader` moved to `commons-io`; since it is not a transitive Maven dependency, it must be declared explicitly with version `2.18.0`.
- **Flyway V2 seed migration is essential for integration tests**: After `flyway.clean() + migrate()` the DB is empty; every integration test that calls `repository.findAll().get(0)` will throw an `IndexOutOfBoundsException` unless a V2 seed migration populates reference data (blocks, rooms, guest rooms, parking zones).
- **Bounded availability query pattern**: The engine fetches exactly 3 queries (all rooms, all timetable slots for the day, all booking items for the day) regardless of room count. All filtering (capacity, block, features, overlap) is done in-memory on the pre-fetched lists — no N+1.
- **Pure POJO engine is easier to test**: `RoomAvailabilityEngine` has zero Spring dependencies; unit tests create entities directly, pass lists in, assert on records out — no `@SpringBootTest` context, no DB, instant feedback.
- **Timetable exclusion constraint**: PostgreSQL `EXCLUDE USING gist (room_id WITH =, academic_term WITH =, day_of_week WITH =, int4range(start_minute, end_minute, '[)') WITH &&) WHERE (active = TRUE)` prevents overlapping timetable slots at the DB level; `DataIntegrityViolationException` is caught in the service and re-thrown as `ConflictException`.
- **Touching intervals must NOT overlap**: Business rule requires `10:00–11:00` and `11:00–12:00` to be independent bookable slots. The overlap check uses strict inequality `startA < endB && startB < endA` (not `<=`).

## Phase 2.5: Upload Hardening, Availability Edges, Demo Seed Decoupling
- **Demo Seed Separation**: Demo data containing foreign keys referencing demo users (like bookings and audit logs) must NEVER be placed in versioned Flyway migrations (`V...sql`). Flyway runs before application beans and runs in non-demo profiles (dev, prod, test). Placing demo records in Flyway migrations will trigger FK violations in non-demo profiles and pollute production schemas. All demo seeds belong exclusively in `@Profile("demo")` runtime seeders (`DemoUserSeeder`).
- **File Upload Verification Defense-in-Depth**: Timetable file validation enforces a multi-layer guard: MIME-type check, file extension check, and magic bytes header sniffing (verifying ZIP header `PK\x03\x04` for XLSX and rejecting PE `MZ` or ELF binaries). PDF imports are rejected with explicit HTTP 415.
- **Formula Injection Mitigation**: When exporting data or echoing user input to CSV/Excel, cells beginning with formula trigger symbols (`=`, `+`, `-`, `@`) must be neutralized with a leading single quote (`'`) to protect spreadsheet viewers from arbitrary command execution.
- **Pessimistic Locking on Finite Resources**: Concurrent parking permit allocations must lock the resource row using `PESSIMISTIC_WRITE` (`SELECT ... FOR UPDATE`) inside the transactional boundary to prevent race condition overbooking.

## Phase 3: Booking Engine, Approvals, Concurrency & Append-Only Audit Logs
- **JPA Assigned vs Generated UUIDs**: When using `@GeneratedValue(strategy = GenerationType.UUID)`, manually setting `id = UUID.randomUUID()` in the constructor causes Spring Data JPA's `SimpleJpaRepository.save()` to treat the entity as detached (`isNew` is false), calling `merge()` which throws `ObjectOptimisticLockingFailureException` or `InvalidDataAccessApiUsageException: detached entity passed to persist`. Leaving `id = null` allows Hibernate to generate the identifier natively upon persist.
- **PostgreSQL Double-Booking Exclusion Constraint**: The table constraint `ex_booking_item_no_overlap` (`EXCLUDE USING gist (resource_id WITH =, tstzrange(start_time, end_time, '[)') WITH &&) WHERE (status IN ('CONFIRMED', 'PENDING_APPROVAL'))`) guarantees double-booking prevention at the kernel level across distributed requests. In Spring Boot, `DataIntegrityViolationException` is intercepted and surfaced as HTTP 409 Conflict.
- **PostgreSQL Append-Only Triggers**: Securing audit logs against tampering is implemented via a PostgreSQL `BEFORE UPDATE OR DELETE` row-level trigger that raises an exception, ensuring an immutable write-once ledger even for superusers executing arbitrary SQL.
- **Idempotency Cache Architecture**: Idempotency keys verify request payload hashes (SHA-256). Exact replays return the cached response payload immediately; mismatches on identical keys throw HTTP 422 `BUSINESS_RULE_VIOLATION`.


## Phase 4 & 4.5: Agent System, Deterministic Planner, Real Data, and SSE Events
- **MockMvc Synchronous SSE vs Concurrent Modification**: MockMvc does not support concurrent response header mutations (`HeaderWriterFilter` vs background worker threads). Async thread pool execution must be configurable via `agent.executor.async: false` in test configurations (`src/test/resources/application-test.yml`) so that MockMvc tests stream synchronously without `ConcurrentModificationException`.
- **Test Classpath Resolution Priority**: Maven compiles `src/main/resources` and `src/test/resources` into separate target directories, but `src/test/resources/application-test.yml` overrides `src/main/resources/application-test.yml`. Test properties must be placed in `src/test/resources/application-test.yml`.
- **Data-Driven Deterministic Resource Allocation**: Eliminating canned responses requires dynamic database scanning. `ScriptedPlanner` queries active bookings during the target time window to dynamically exclude booked resources (e.g. guest room `G-101`) and select free resources (e.g. `G-102`) deterministic based on capacity and availability.
- **Audit Logging for Agent Reasoning & Tool Execution**: Every step of the agent's execution is recorded in `audit_logs` as `AGENT_REASONING` and `TOOL_CALL` actions with sanitized arguments, duration, and execution status, directly queryable via `GET /api/admin/audit?action=TOOL_CALL`.
- **Relative Date Parsing in Indian Standard Time**: Relative natural language dates (e.g. "next Thursday") are resolved strictly against `ZoneId.of("Asia/Kolkata")` to prevent day rollover anomalies when server JVMs run in UTC.

## Phase 5: End-to-End Integration, Reports Aggregates, and Security Hardening
- **Windows Junction Directory Resolution**: In Windows environments with directory symlinks/junctions (e.g. `C:\Users\Lokesh\campusflow` -> `C:\Users\Lokesh\Desktop\campusflow`), Node.js tools such as Knip can report false-positive unused files if path resolution switches between junction and target. Running from the canonical directory or configuring paths correctly ensures pristine verification.
- **Reports SQL Aggregation**: Utilisation reports (`GET /api/admin/reports/utilisation`) aggregate booking minutes, hourly distribution, and peak hours using bounded SQL queries grouped by hour and day without N+1 overhead.
- **Public vs Protected Announcement**: `GET /api/content/announcement` is made accessible without authentication to allow pre-login status announcements, while administrative updates remain strictly protected under `ROLE_ADMIN`.
- **Automated End-to-End Acceptance**: Automating the complete multi-role flow (`EndToEndAcceptanceFlowIntegrationTest`) validates the full handover: Staff agent conversation -> Timetable conflict -> Alternatives -> Proposal -> Booking submission (PENDING) -> Admin approval -> Calendar update -> Immutable audit trail.
